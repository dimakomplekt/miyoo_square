# MIYOO SQUARE

## 1. Что это за игра

**MIYOO SQUARE** — небольшая экспериментальная 2D-игра для Miyoo Mini+, созданная на C++ поверх SDL2. Игрок управляет квадратом: он перемещается по сцене, прыгает, сталкивается с полом и стенами, сжимается при таране в стену, восстанавливает форму и отскакивает обратно.

На поверхности это простая игра, но её настоящая задача — быть лабораторией для собственного игрового движка. Идея проекта: **сделать движок для более крупной игры, начиная с менее крупной игры**. Минимальный игровой сценарий позволяет проверить сразу несколько фундаментальных механизмов:

- обработку ввода и событий;
- движение, таймеры и delta time;
- столкновения и разрешение пересечений;
- переходы между состояниями объектов;
- загрузку и смену ассетов;
- жизненный цикл игровых объектов;
- обновление и рендеринг в реальном времени;
- работу state machine.

Поэтому простота игры — не ограничение, а сознательный выбор. Чем меньше игровой сценарий, тем легче увидеть, как именно работают архитектурные слои.

## 2. Архитектура проекта

Проект разделён на два крупных уровня:

- `app` — конкретное приложение, его состояния, игровые объекты и правила игры;
- `engine` — переиспользуемые модули движка.

Внизу находится SDL2 и связанные библиотеки SDL_image/SDL_ttf. SDL отвечает за окно, renderer, события, поверхности, текстуры, ввод и базовую работу платформенного слоя. Игровая логика не должна напрямую превращаться в набор SDL-вызовов: она использует объекты и менеджеры более высокого уровня.

### Application layer

Папка `libs/app` содержит:

- запуск приложения и главный цикл;
- регистрацию игровых состояний;
- глобальные данные приложения;
- таймер;
- игровые объекты;
- движение объектов;
- конкретную игровую сцену MIYOO SQUARE.

Здесь находятся `START`, `MAIN_MENU` и `GAME`, а также заготовка для создания новых состояний.

### State machine

State machine хранит состояния приложения, связывает их по идентификаторам и вызывает назначенные callbacks. Каждый state использует общий жизненный цикл:

```text
enter
  -> create / init
  -> setup
  -> update
  -> render
  -> exit / destroy
```

В коде это разделено на несколько уровней:

1. `on_enter` — вход в состояние;
2. создание элементов состояния;
3. настройка позиций, размеров и начальных значений;
4. `state_update` — обновление ввода, игровой логики и событий;
5. `state_render` — отрисовка;
6. `on_exit` — освобождение ресурсов и выход.

Общее для состояний — одинаковый контракт callbacks, регистрация в state machine, возможность перехода в другое состояние и разделение update/render. Благодаря этому игровой экран, главное меню и будущие состояния могут жить по одной схеме.

Внутри игрового состояния дополнительно выделены функции сцены:

```text
scene_create
scene_setup
scene_update
scene_actions
scene_render
scene_destroy
```

Это позволяет не смешивать жизненный цикл самого state с логикой конкретной сцены.

### Asset manager и instance manager

Asset — это загруженный ресурс: изображение, шрифт или другой тип данных, которым владеет движок. Instance — конкретное использование asset в сцене. Один asset может иметь несколько instance, расположенных в разных местах и используемых разными объектами.

`Asset_manager` отвечает за регистрацию, загрузку и удаление ресурсов. `Instance_manager` создаёт и обслуживает инстансы, выдаёт им handles, следит за подписчиками и позволяет безопасно разделять один ресурс между несколькими владельцами.

Такое разделение полезно потому что:

- ресурс не приходится загружать заново для каждого объекта;
- объекты работают через handles, а не через хаотичный набор указателей;
- жизненный цикл asset и instance можно контролировать отдельно;
- один и тот же asset можно использовать в разных игровых объектах.

### GUI-элементы

В `engine/logic_modules/program_gui` находятся базовые элементы интерфейса:

- базовый SDL-элемент;
- panel;
- button;
- textbox;
- texture;
- fader;
- функции рисования и преобразования цветов.

Эти элементы собираются из общих компонентов и могут обновлять свои размеры, цвета, текст, шрифты и состояние во время работы приложения.

### Глобальные палитры и шрифты

Глобальные менеджеры палитры цветов и шрифтов связаны с GUI-слоем. Это позволяет менять визуальные параметры централизованно, не проходя вручную по каждому UI-элементу. Элемент получает общую настройку и может обновиться при runtime-изменении палитры или выбранного шрифта.

Это особенно удобно для:

- смены темы;
- локализации;
- визуальных состояний кнопок;
- цветовых переходов;
- единообразного оформления интерфейса.

### Язык и `lang_state`

Модуль `program_logic/lang_state` содержит типы языка, словари и состояние текущей локали. Словарь хранит значения для интерфейса, а `lang_state` отвечает за выбранный язык и сигнализирует, что UI необходимо обновить.

Таким образом, текст интерфейса отделён от логики кнопок и экранов. Состояние может запросить перевод по ключу, а не хранить все строки непосредственно внутри игрового кода.

### Таймер и программный pipeline

`App_timer` предоставляет реальное время и delta time. Игровой pipeline разделён на частоты выполнения:

- ввод обновляется часто;
- логика обновляется отдельной зоной;
- рендер работает в своей зоне;
- движение использует delta time, поэтому не должно зависеть от количества кадров.

Общий путь кадра выглядит так:

```text
SDL events
  -> input manager
  -> current state
  -> actions / movement requests
  -> movement update
  -> collision checks
  -> state and object updates
  -> render
```

## 3. Ассеты и игровые объекты

Игровые объекты сцены — фон, пол, стены и квадрат — находятся в `app/game_objects`. Они используют assets через instance handles, но сами добавляют игровую семантику:

- положение и размеры;
- hitbox;
- генерацию составных поверхностей;
- обработку столкновений;
- движение;
- переключение внешнего вида;
- собственные состояния.

Квадрат — наиболее показательный объект проекта. Его движение отделено в `objects_movement`, а реакция на стену оформлена как state machine:

```text
MOVING
  -> COMPRESSING
  -> RECOVERING
  -> BOUNCING
  -> MOVING
```

Это демонстрирует, как поверх базовых движка и SDL можно строить более выразительную игровую механику.

### Сильные стороны подхода

- понятное разделение engine/app;
- переиспользуемые менеджеры ресурсов;
- единый жизненный цикл состояний;
- возможность добавлять новые GUI-элементы и состояния;
- независимое развитие игровой логики и платформенного слоя;
- хорошая учебная наблюдаемость: отдельные системы можно проверять на маленьком игровом сценарии.

### Компромиссы

Архитектура пока рассчитана прежде всего на обучение и развитие движка. В ней ещё есть места для будущей унификации, автоматизации и расширения: например, для более сложных сцен, аудио, ресурсов разных типов, физики и инструментов разработки. Это сознательная стадия проекта, а не попытка представить маленький эксперимент как готовый промышленный движок.

```text
miyoo_square/
├── CMakeLists.txt                 # Сборка проекта
├── build_windows.ps1              # Сборка Windows
├── build_miyoo.sh                 # Сборка под Miyoo
├── deploy_on_wifi.ps1             # Перенос сборки по Wi-Fi
├── check_miyoo_build.sh           # Проверка Miyoo-сборки
├── cmake/                         # Toolchain и настройки CMake
├── diary/                         # Дневник разработки и документация
│   └── about/                     # Обзор проекта и иллюстрации
├── libs/
│   ├── app/                       # Конкретное приложение MIYOO SQUARE
│   │   ├── game_objects/          # Игровые объекты и движение
│   │   ├── global_data/           # Таймер, словарь и данные приложения
│   │   └── program_states/        # State machine и состояния игры
│   └── engine/                    # Переиспользуемая часть движка
│       ├── base_modules/          # SDL2 и Miyoo toolchain
│       └── logic_modules/
│           ├── asset/              # Assets, instances и их менеджеры
│           ├── program_gui/        # GUI, палитры, шрифты и drawing
│           └── program_logic/      # Input, language и state machine
├── app_content/                   # Контент, копируемый в runtime-сборку
└── build_*/                       # Результаты локальной сборки
```

## 5. Основные функции программного pipeline

| Этап | Назначение | Где реализуется |
|---|---|---|
| Инициализация SDL | Окно, renderer, SDL_image и SDL_ttf | `libs/app/app.cpp`, `libs/engine/base_modules/SDL` |
| Создание менеджеров | Asset и instance lifetime | `libs/app/app.cpp`, `libs/engine/logic_modules/asset` |
| Регистрация состояний | Добавление states и callbacks | `libs/app/program_states/program_states.cpp` |
| Вход в state | Создание объектов и ресурсов сцены | `libs/app/program_states/states_logic` |
| Настройка сцены | Позиции, размеры, начальные параметры | `libs/app/program_states/states_logic/2.0_GAME` |
| Обработка ввода | Keyboard и action mapping | `libs/engine/logic_modules/program_logic/global_inputs` |
| Обновление времени | Delta time и зоны выполнения | `libs/app/global_data/app_timer` |
| Движение | Запросы, скорость и стадии движения | `libs/app/game_objects/objects_movement` |
| Коллизии | Hitbox и разрешение пересечений | `libs/engine/logic_modules/asset`, игровые объекты |
| Игровая реакция | Прыжок, сжатие, восстановление, bounce | `libs/app/game_objects/square_game_objects/square` |
| GUI | Панели, кнопки, текст, fader и texture | `libs/engine/logic_modules/program_gui` |
| Локализация | Словарь и текущее состояние языка | `libs/engine/logic_modules/program_logic/lang_state` |
| Обновление сцены | `update`, actions и игровые события | `libs/app/program_states/states_logic` |
| Рендер | Фоновый слой, объекты и GUI | `libs/app`, `libs/engine/logic_modules/program_gui` |
| Выход из state | Очистка объектов, instances и assets | `libs/app/program_states/states_logic` |

## Итог

MIYOO SQUARE — завершённая маленькая игра и одновременно первый полноценный полигон собственного движка. Её ценность не в количестве механик, а в том, что на понятной сцене были собраны и проверены базовые элементы настоящего игрового проекта: приложение, состояния, ресурсы, ввод, движение, столкновения, GUI, локализация и рендер.

Это первый законченный шаг к более крупным проектам, для которых движок будет развиваться дальше.

И особенно символично, что он завершён в День программиста.
