# Архитектура игровой системы

## Общая идея

Игровая система строится поверх существующего движка PSMVA и постепенно расширяет его до универсального игрового runtime.

Главный принцип архитектуры:

> Игровые объекты описывают состояние и поведение игры, а движок предоставляет им необходимые возможности: работу с ассетами, графикой, аудио и GUI.

Архитектура не должна реализовывать все возможные игровые механики заранее. На первом этапе реализуется только необходимый минимум, при этом базовая структура должна позволять постепенно добавлять новые возможности без перестройки всей системы.

---

## Основные подсистемы движка

### Asset Manager

`AssetManager` отвечает за регистрацию и жизненный цикл ассетов.

Ассетом является либо непосредственно ресурс, либо экземпляр/ссылка на существующий ресурс.

Основные категории:

* аудио;
* визуальные ресурсы;
* ссылки на уже существующие ресурсы.

При создании ассет регистрируется в `AssetManager`.

При уничтожении ассет снимается с регистрации.

Asset Manager не обязан управлять всей логикой использования ресурса. Его основная задача заключается в централизованном учёте существующих ассетов и обеспечении их доступности другим подсистемам.

---

### Renderer

`Renderer` отвечает за отображение визуальных объектов.

Он работает с визуальными ассетами и GUI-объектами, не занимаясь игровой логикой.

Конкретный визуальный объект может представлять собой:

* изображение;
* текстуру;
* текст;
* спрайт;
* другой тип визуального представления.

Конкретная реализация объекта скрыта от игрового объекта.

---

### Audio Player

`AudioPlayer` отвечает за воспроизведение аудио.

Игровые и GUI-объекты не должны напрямую работать с низкоуровневым SDL-аудио API.

Вместо этого они обращаются к своим аудио-объектам:

```cpp
audio.play();
```

а уже аудио-объект взаимодействует с `AudioPlayer` и соответствующим ассетом.

Это позволяет игровой логике не зависеть от конкретной реализации аудиосистемы.

---

### GUI

GUI состоит из самостоятельных объектов, имеющих собственное состояние и жизненный цикл.

GUI-объект может использовать различные типы визуальных ресурсов и при этом предоставлять единый интерфейс для игрового объекта.

Например:

```cpp
gui_object.move();
gui_object.set_position();
gui_object.set_visible();
gui_object.render();
```

Конкретный GUI-объект при этом может представлять изображение, текстуру, текст или другой тип визуального элемента.

GUI-объект также определяет правила владения используемыми ресурсами.

Он может:

* владеть ассетом и уничтожить его при своём уничтожении;
* использовать существующий ассет как экземпляр/ссылку, не уничтожая исходный ресурс.

# Игровые объекты

## GameObject

Базовая сущность игровой логики.

`GameObject` не обязан иметь графическое или аудио представление.

Он может существовать исключительно для хранения состояния и выполнения логики.

Например:

```text
QuestState
GameTrigger
WorldState
```

могут быть игровыми объектами, несмотря на отсутствие графики и звука.

Базовый объект предоставляет общий жизненный цикл и возможность обновления состояния.

---

## Композиция игровых объектов

Игровой объект может композиционно владеть другими объектами:

```text
Character
├── state
├── GUI objects
├── Audio objects
└── другие игровые данные
```

При этом игровой объект не обязан напрямую знать о конкретной реализации используемых подсистем.

Например:

```cpp
character.move(dx, dy)
{
    position += delta;

    body.move(delta);
    name.move(delta);
}
```

`body` может быть изображением, спрайтом, текстурой или другим визуальным объектом.

`Character` работает с предоставленным интерфейсом, а не с конкретной реализацией.

---

# Состояние игровых объектов

Игровой объект может содержать произвольное состояние, необходимое конкретной сущности.

Например:

```text
Character
├── HP
├── max HP
├── position
├── inventory
├── state
└── ...
```

Другой объект может содержать совершенно другой набор данных:

```text
Quest
└── quest state
```

или:

```text
Chest
├── inventory
├── state
└── GUI
```

Таким образом, наличие графики, аудио или инвентаря не является обязательным свойством базового игрового объекта.

---

# Наследование и композиция

Наследование используется для описания типа игровой сущности:

```text
GameObject
├── Character
├── Item
├── Chest
├── Trigger
└── ...
```

Композиция используется для добавления конкретных возможностей:

```text
Character
├── CharacterState
├── Inventory
├── GUI
└── Audio
```

Таким образом:

> Наследование определяет, чем является объект, а композиция определяет, чем он обладает.

Конкретная граница между наследованием и композицией не фиксируется заранее и может изменяться по мере развития проекта.

---

# Пример простого игрового объекта

Не каждый объект должен иметь полноценное представление.

Например, фоновое пение птиц может быть игровым объектом:

```text
BirdsChirp
├── state
└── AudioObject
```

Он может существовать в игровом мире, обновляться вместе с остальными объектами и периодически инициировать воспроизведение звука.

Аналогично могут существовать:

```text
Rain
├── state
└── AudioObject
```

```text
Torch
├── state
├── GUIObject
└── AudioObject
```

```text
Quest
└── state
```

Все они являются игровыми объектами, несмотря на различия в представлении.

# Жизненный цикл ресурсов

Общий принцип работы с ресурсами:

```text
create
   ↓
register in AssetManager
   ↓
use
   ↓
destroy
   ↓
unregister from AssetManager
```

Если объект использует существующий ресурс как экземпляр:

```text
Asset A
   │
   └── Asset Instance B
```

уничтожение `B` не должно автоматически уничтожать `A`.

Таким образом, lifetime объекта и lifetime исходного ресурса могут существовать независимо.

---

# Платформенная абстракция

Игровая логика не должна зависеть от конкретной платформы.

Архитектура должна позволять использовать один и тот же игровой код на разных платформах:

```text
                    GAME
                     │
                   ENGINE
                     │
             ┌───────┴───────┐
             │               │
          Windows           Miyoo
             │               │
           SDL2             SDL2
             │               │
        SDL2_image       SDL2_image
        SDL2_ttf         SDL2_ttf
```

Платформенные различия должны находиться ниже уровня игровой логики.

# Принцип развития

Архитектура является первоначальной точкой отсчёта, а не окончательной спецификацией.

На первом проекте реализуется только необходимая часть системы.

Не требуется заранее реализовывать:

* полноценную систему инвентаря;
* сложную систему событий;
* анимационную систему;
* физику;
* частицы;
* квестовую систему;
* ECS;
* сетевой слой;
* другие потенциальные подсистемы.

Если новая функциональность потребуется, она добавляется в существующую структуру.

Главная цель первоначальной архитектуры:

> Создать достаточно прозрачную систему, в которой очевидно, где находится состояние, где находится представление, где работают ассеты, где работает аудио и где находится игровая логика.

Архитектура должна масштабироваться не за счёт предварительной реализации всех возможных возможностей, а за счёт того, что новые возможности можно добавлять без необходимости переписывать существующие уровни системы.
