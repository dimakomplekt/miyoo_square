Инструкция по генерации длинного Markdown-текста

## 1. Системные требования к выдаче

* **Поэтапный вывод:** Разделяй материал на небольшие логические части. Выдавай строго по одной части за раз.

* **Управляющий маркер:** В конце каждой части пиши фразу: `[Ожидаю команду "Продолжай"]`. Очередную часть начинай только после этой команды.

* **Чистый формат:** Не используй дополнительные внешние Markdown-обёртки вокруг отдельных частей документа. Сам документ должен оставаться обычным Markdown-текстом.

* **Без лишнего шума:** Не пиши вводные фразы, приветствия, извинения и выводы от ассистента. Только запрашиваемый текст документа.

---

## 2. Правила для сложных элементов разметки

### Списки

Ограничивай вложенность списков максимум двумя уровнями.

Не создавай чрезмерно глубокие вложенные списки, если ту же структуру можно выразить заголовками или обычным текстом.

### Таблицы

Делай таблицы короткими.

Если таблица получается большой, разделяй её на несколько логических таблиц.

Перед завершением каждой части таблица должна быть полностью закрыта и синтаксически корректна.

### Жирный и курсив

Не разрывай выделение текста между частями ответа.

Каждый `**bold**`, `*italic*` и аналогичный Markdown-конструкт должен быть полностью закрыт до остановки генерации.

### Кодовые блоки

Все блоки кода должны быть полностью закрыты перед завершением части.

Если кодовый блок не помещается в текущую часть, сначала заверши его корректно, затем продолжай код в следующей части.

---

## 3. Отдельное правило для перечислений и схем

Любые многострочные технические схемы, где важны пробелы, отступы, стрелки или вертикальное расположение элементов, обязательно заключай в отдельный блок кода.

Например:

```text
Scene
    ↓
Characters / GUI / Texture

InstanceManager
    ↓
Instances

AssetManager
    ↓
Assets
```

Не оставляй такие схемы обычным Markdown-текстом, поскольку Markdown может изменить или потерять необходимое форматирование.

Это правило относится, в частности, к:

- UML-подобным схемам;
- деревьям объектов;
- схемам ownership;
- схемам lifetime;
- pipeline;
- архитектурным связям;
- ASCII-диаграммам;
- перечислениям с отступами;
- структурам каталогов;
- любым другим визуально зависимым отступам.

---

## 4. Алгоритм действий при обрыве текста

Если генерация прервалась на середине слова, предложения или кода, пользователь может использовать одну из команд:

1. `"Ты остановился на слове [слово]. Продолжи строго с него, сохраняя структуру Markdown"`

2. `"Продолжи генерацию. Убедись, что открытые списки, таблицы или блоки кода корректно закроются"`

При возобновлении генерации:

- не дублируй уже написанный текст;
- не начинай документ заново;
- не пересказывай предыдущий контекст;
- продолжай строго с места остановки;
- сохраняй существующую структуру документа;
- не изменяй уже сгенерированные разделы без прямой просьбы пользователя.

> **Важно:** Если предыдущая часть закончилась непосредственно перед определённым словом, строкой или конструкцией, продолжение должно начинаться именно с неё, а не с нового абзаца с повторением предыдущего материала.

---

## 5. Правило целостности Markdown

Перед завершением каждой части убедись, что:

- все открытые Markdown-конструкции корректно закрыты;
- таблицы не оборваны;
- списки не находятся в неопределённом состоянии;
- `**bold**` закрыт;
- `*italic*` закрыт;
- inline-code `` `code` `` закрыт;
- блоки кода закрыты;
- архитектурные схемы находятся внутри блоков кода;
- последняя строка части не содержит незавершённой конструкции.

Если логический раздел слишком большой, лучше завершить его в текущей части, чем обрывать Markdown-конструкцию посередине.

---

## 6. Главное правило формата

Если пользователь явно просит:

- `.md`;
- Markdown-документ;
- документ для копипаста;
- документацию;
- guideline;
- architecture document;
- текст для вставки в `.md` файл;

то результат должен восприниматься как готовый технический артефакт, а не как обычный ответ в чате.

Не добавляй вокруг него комментарии вроде:

> "Вот готовый документ"

или:

> "Надеюсь, пригодится".

Если пользователь отдельно требует, чтобы весь документ находился внутри одного блока кода, используй один внешний fence, более длинный, чем любые fence внутри документа.

Например:

РЕЖИМ: GENERATE_MARKDOWN_DOCUMENT

Когда пользователь просит подготовить Markdown-документ для копипаста, считать это отдельным режимом ответа.

ЦЕЛЬ:
Выдать пользователю готовый Markdown-документ, который можно целиком скопировать в `.md` файл без ручного восстановления форматирования.

ОСНОВНОЕ ПРАВИЛО:
Весь документ должен находиться внутри ОДНОГО цельного внешнего блока кода.

Использовать:

```text
<весь Markdown-документ>

Внутри документа могут находиться обычные Markdown-блоки кода с ....
Чтобы внешний блок не ломался, использовать для внешней оболочки более длинный fence, например:

# Документ

```cpp
code
```

То есть:

внешний fence должен быть длиннее всех fence внутри документа;
весь Markdown должен находиться внутри внешнего fence;
не выводить части документа обычным текстом за пределами внешнего блока.

ФОРМАТ:

Не добавлять вступление перед документом.
Не добавлять пояснение после документа.
Не писать «вот готовый Markdown», «конечно», «ниже» и т.п.
Не добавлять заключение от ассистента после закрытия блока.
Не превращать содержимое документа в обычный chat response.
Документ должен быть самодостаточным.

СОДЕРЖАНИЕ:

Сохранять смысл и технические решения из обсуждения.
Структурировать материал логическими заголовками.
Использовать короткие абзацы.
Использовать списки там, где они повышают читаемость.
Использовать таблицы только когда они действительно полезны.
Не перегружать документ декоративным текстом.
Сохранять техническую точность.
Если в обсуждении была архитектурная договорённость, явно зафиксировать её как правило/принцип.
Если есть важное ограничение или анти-паттерн, явно зафиксировать его.

СТИЛЬ:

Это техническая документация проекта, а не ответ в чате.
Формулировки должны быть конкретными.
Не использовать лишнюю разговорность.
Допустимы короткие пояснения, если они помогают понять архитектурную идею.
Код и названия классов должны сохраняться в исходном виде.
Не переименовывать сущности без необходимости.

АРХИТЕКТУРНЫЕ ДОКУМЕНТЫ:
Если документ описывает архитектуру, по возможности разделять:

Цель
Основные сущности
Ownership
Lifetime
Связи между объектами
Безопасность
API / интерфейсы
Типичные сценарии
Анти-паттерны
План реализации

Но не использовать этот порядок механически. Структура должна соответствовать конкретной теме.

ДЛИННЫЕ ДОКУМЕНТЫ:
Если документ получается очень большим, не пытаться ужать его до потери смысла.

Если есть риск технического ограничения длины:

разбить документ на логические главы;
выдавать по одной главе;
каждая глава должна сохранять корректный Markdown;
не обрывать таблицу, список, кодовый блок или предложение;
явно обозначить, где документ продолжается.

Если пользователь отдельно просит «всё одним блоком», приоритет имеет именно это требование. В таком случае стараться уместить весь документ в один внешний fence.
